LeanRDF 0.4.0 makes answers proof-carrying. An agent that derives a fact from RDF data can now hand over a certificate. Anyone can check it with a small verified program, and the certificate states what data, query and rules it is about.

## leanrdf-check

`check/` is a new package, `leanrdf-check`. It contains the verified checker and the OWL rules, and no search: it does not depend on lean-elpi.

```sh
leanrdf-check --data DATA --query QUERY --cert CERT.json [--rules simple|rdf|rdfs|owl|el] [--json] [--emit-envelope OUT.json]
```

- Five regimes: `simple`, `rdf`, `rdfs`, `owl` (OWL 2 RL) and `el` (OWL 2 EL). `checkRegime_sound` turns an accepted certificate into the regime's entailment: `SimpleEntails`, `RDFEntails`, `RDFSEntails` or `OWLEntails`.
- Verdicts with fixed exit codes, the same for every LeanRDF tool from now on: `proven` 0, `unknown` 1, `rejected` 2, `input-error` 3, `inconsistent` 4, `refuted` 5. `leanrdf-check` produces 0, 2 and 3. `--json` writes the verdict as one object, for agents.
- A recorded corpus of 21 certificates across the five regimes, tampered ones included, runs in `lake test`.

## Certificate version 2

A version-2 certificate carries an `envelope`:

- `graph` and `query`: the digests of the data and the query;
- `rules`: the rule set's name and digest;
- `regime`, and the `theorem` an acceptance stands for;
- `checker` and `toolchain`.

`leanrdf-check` recomputes the digests from the files it reads before it checks the proof. A certificate checked against other data, another query, other rules or another regime is rejected (`envelope: graph digest mismatch`, and so on), even if its proof would pass. `leanrdf-demo` writes version 2.

Version 1 is still read. Its verdict says the certificate is unbound, and `--emit-envelope` writes it as version 2 after a successful check.

## RDFC-1.0 and digests

`LeanRDF.Canon` implements W3C RDF Dataset Canonicalization (RDFC-1.0) in Lean, with no dependency. `Graph.digest` and `Dataset.digest` are `sha256:` and the SHA-256 of the canonical N-Quads, the identity that RDFC-1.0 and Verifiable Credentials use. Two parties holding the same data compute the same digest, whatever the triple order and blank-node labels of their files.

- The whole W3C rdf-canon suite passes: 64 evaluation tests, 21 issued-label tests, and the negative poison-graph test, which hits the work limit instead of hanging.
- Blank nodes inside RDF 1.2 triple terms are canonicalized by an extension of LeanRDF's own. RDFC-1.0 predates triple terms.
- SHA-256 moved from `leanrdf-sparql` to the core (`LeanRDF.Text.Hash`). SPARQL's hash functions re-export it, and the SPARQL suite is unchanged.

## What is proven and what is trusted

- Proven, with only `propext`, `Quot.sound` and `Classical.choice`:
  - `checkRegime_sound`;
  - `canonicalLabels_injective`: the canonical relabeling is a bijection on blank nodes;
  - `canonical_iso`: the canonical dataset is isomorphic to its input.
- Tested, not proven:
  - canonicity, that isomorphic inputs get equal output (on the W3C suite);
  - SHA-256 (on the NIST vectors).
- The envelope is outside the trusted base. The checker never reads it, so a bug in digests can reject a good certificate or bind a proof to the wrong name, but cannot make a wrong proof pass. The proven statement is always about the graph that was parsed.
- `native_decide` in tests trusts the Lean compiler, as before.
